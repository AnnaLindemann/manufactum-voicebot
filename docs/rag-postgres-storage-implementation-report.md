# Отчёт о реализации: постоянное хранилище PostgreSQL для версионирования документов RAG

## Фаза

Реализация постоянного хранилища на PostgreSQL для уже существующего потока версионирования документов
RAG (`D-004`). Ранее хранилище было только in-memory за интерфейсом `RagDocumentStore`; теперь добавлена
реализация на PostgreSQL, которая является drop-in заменой этого интерфейса. In-memory реализация
сохранена для юнит-тестов.

В рамках задачи **не добавлялись**: Supabase SDK, Prisma, pgvector, эмбеддинги, эндпоинты ретрива,
краулинг, планировщик и любые новые возможности RAG. Использован минимальный клиент PostgreSQL (`pg`)
и SQL-миграции. Существующего подхода к базе данных в репозитории не было, поэтому выбран минимальный
клиент — как и предписано.

## Изменённые и добавленные файлы

- `src/rag/document-store.ts` — **изменён.** Интерфейс `RagDocumentStore` сделан асинхронным
  (методы возвращают `Promise`). Это необходимо, потому что клиент `pg` асинхронен по своей природе;
  без этого реализация на PostgreSQL не могла бы стоять за существующим интерфейсом. Типы хранимых
  записей (`DocumentVersionCore`, `StoredDocumentVersion`, `ChunkCore`, `StoredChunk`,
  `StoredDocument`, `NewVersionInput`) не менялись.
- `src/rag/in-memory-document-store.ts` — **изменён.** Методы приведены к асинхронной сигнатуре
  интерфейса; внутренняя логика, инварианты и неизменяемость сохранены без изменений. Реализация
  по-прежнему используется юнит-тестами.
- `src/rag/ingest-faq-page.ts` — **изменён.** Поток загрузки стал `async`/`await` в местах вызова
  хранилища (`getDocument`, `appendVersion`). Логика обнаружения изменений и версионирования не
  изменилась.
- `src/rag/postgres-document-store.ts` — **новый.** Реализация `PostgresRagDocumentStore` за
  интерфейсом `RagDocumentStore`.
- `src/rag/migrate.ts` — **новый.** Минимальный forward-only раннер SQL-миграций (`runMigrations`),
  без фреймворка и ORM. Принимает уже сконфигурированный `pg.Pool`; строку подключения не читает.
- `scripts/migrate.ts` — **новый.** Явная команда миграции `npm run migrate`.
- `migrations/0001_rag_document_store.sql` — **новый.** Схема: документы, неизменяемые версии,
  неизменяемые чанки, плюс триггеры неизменяемости.
- `tests/integration/rag-postgres-document-store.test.ts` — **новый.** Опциональные интеграционные
  тесты, работающие только при заданном `RAG_TEST_DATABASE_URL`.
- `tests/unit/rag-ingest-faq-page.test.ts`, `tests/unit/rag-in-memory-document-store.test.ts` —
  **изменены.** Приведены к `async`/`await` под асинхронный интерфейс (ошибки проверяются через
  `rejects.toThrow`).
- `package.json` — добавлен скрипт `migrate`; добавлены зависимости `pg` и dev-зависимость
  `@types/pg`. `.env.example` — задокументированы `DATABASE_URL` и `RAG_TEST_DATABASE_URL` (только
  имена, без значений).

## Схема данных (`migrations/0001_rag_document_store.sql`)

- `rag_documents` — по одной строке на ключ документа. Единственное **изменяемое** поле —
  `current_version`, указатель на активную версию. Всё остальное об активной версии (source URL,
  title, content hash, …) выводится соединением (`JOIN`) с соответствующей строкой
  `rag_document_versions`. `created_at` — время создания версии 1 (стабильный `createdAt` документа).
- `rag_document_versions` — append-only, неизменяемые. Первичный ключ `(document_key, version)`,
  внешний ключ на `rag_documents`. Несёт весь контент и трассируемые метаданные версии.
- `rag_chunks` — append-only, неизменяемые. Первичный ключ `(document_key, document_version,
chunk_index)`, внешний ключ на `(document_key, version)`. Столбец `chunk_key` уникален и хранит
  утверждённый формат `{document_key}:v{document_version}:chunk-{zero-padded 1-based index}`.
- **Триггеры неизменяемости** на `rag_document_versions` и `rag_chunks` запрещают `UPDATE` и `DELETE`
  на уровне БД (`BEFORE UPDATE OR DELETE`). `current_version` живёт на `rag_documents`, который
  остаётся свободно обновляемым, — так неизменяемость версий/чанков гарантируется даже вне приложения.

Признак `isActive` **не хранится**, а выводится на чтении: версия активна тогда и только тогда, когда
её номер равен `rag_documents.current_version`.

## Реализованное поведение

### Атомарность записи

`appendVersion` выполняется в одной транзакции. Она блокирует строку документа (`SELECT …
FOR UPDATE`), чтобы конкурентные добавления по одному ключу сериализовались, проверяет непрерывность
номера версии, вставляет строку версии и все строки чанков и, для существующего документа, обновляет
**только** `current_version`. При любой ошибке выполняется `ROLLBACK`, поэтому частично записанная
версия никогда не наблюдаема. Первая версия дополнительно создаёт строку `rag_documents` с
`current_version = 1`.

### Сравнение хеша с активной версией

Обнаружение изменений остаётся в потоке загрузки (`ingest-faq-page.ts`) и не менялось: поток читает
`getDocument().contentHash` (хеш активной версии) и сравнивает с входящим `contentHash`.

- **Тот же хеш** → поток не вызывает `appendVersion`, новая версия не создаётся, активная версия не
  меняется (`outcome: "unchanged"`).
- **Изменённый хеш** → поток вызывает `appendVersion` со следующим номером версии; создаётся новая
  версия и её чанки, и обновляется только `current_version`.

### Неизменяемость старых версий и чанков

Старые версии и чанки никогда не изменяются и не удаляются. Активация новой версии — это только сдвиг
указателя `current_version`; строки предыдущих версий остаются байт-в-байт прежними, а их `isActive`
выводится как `false`. Это подкреплено триггерами БД.

### Трассируемость и метаданные

Каждая версия и каждый чанк несут все обязательные метаданные из `rag-design.md` (document key,
document version, chunk index/key/hash, source URL, title, document type, language, created time,
active flag (вычисляемый), crawler version, extractor version). Значения приходят из потока загрузки и
реестра источников — хранилище ничего не выдумывает. `created_at` хранится как `timestamptz` и
возвращается как ISO-8601 (`Date.toISOString()`), что для значений, порождённых потоком (канонический
ISO с миллисекундами), даёт точный round-trip.

### Тот же контракт и те же инварианты

`PostgresRagDocumentStore` — drop-in замена `InMemoryRagDocumentStore`: чтения возвращают свежие
замороженные (`Object.freeze`) представления с выведенным `isActive`, списки упорядочены по возрастанию
(версии по номеру, чанки по `chunkIndex`), а `appendVersion` отклоняет некорректную нумерацию версий и
чанки, не принадлежащие добавляемой версии, — с той же ошибкой `RagStorageError`, что и in-memory.

## Команда миграции

- `npm run migrate` (`scripts/migrate.ts`) читает строку подключения из `DATABASE_URL`, применяет все
  ожидающие SQL-файлы из `migrations/` в порядке имён и печатает **только** имена применённых файлов.
- Применённые миграции фиксируются в таблице `schema_migrations`; повторный запуск идемпотентен. Каждый
  файл выполняется в своей транзакции вместе с записью в `schema_migrations`.
- Команда требует реальную БД, не имеет in-memory-фолбэка и **не вызывается** из `npm run check`.

## Интеграционные тесты

`tests/integration/rag-postgres-document-store.test.ts` запускаются **только** при заданном
`RAG_TEST_DATABASE_URL` (иначе вся сюита пропускается через `describe.skipIf`). Они применяют миграции,
затем проверяют: первую загрузку (v1 + активные чанки), отсутствие новой версии при неизменном хеше,
создание v2 с сохранением неизменной неактивной v1, атомарность (сбой в середине транзакции не
оставляет ничего), отклонение непрерывной нумерации и запрет `UPDATE` на уровне БД. База считается
одноразовой: перед каждым тестом таблицы очищаются `TRUNCATE`.

Локально интеграционные тесты **не выполнялись** против живой БД: в окружении недоступны Docker-демон и
локальный PostgreSQL. Тесты подключены и корректно пропускаются; `npm run check` не требует БД.

## Безопасность

Код нигде не читает, не печатает, не логирует и не коммитит содержимое `.env` или строки подключения.
Строка подключения берётся из переменных окружения (`DATABASE_URL` / `RAG_TEST_DATABASE_URL`); сообщения
об ошибках называют только имя переменной. `.env.example` содержит только имена переменных без значений.

## Допущения и ограничения объёма

- Интерфейс `RagDocumentStore` переведён на `Promise`-контракт — это необходимое условие, чтобы за ним
  могла стоять асинхронная реализация PostgreSQL. In-memory-реализация резолвит синхронно; асинхронная
  сигнатура помечена локальным `eslint-disable @typescript-eslint/require-await` с пояснением.
- Строка подключения передаётся как `connectionString`; отдельная настройка TLS/SSL не добавлялась, её
  при необходимости несёт сама строка подключения (например, `sslmode=require`).
- Вне рамок фазы (и не добавлялось): Supabase SDK, Prisma, pgvector, эмбеддинги, эндпоинты ретрива,
  краулинг, планировщик, любые новые возможности RAG.
