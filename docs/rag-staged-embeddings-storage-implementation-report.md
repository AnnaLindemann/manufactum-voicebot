# Отчёт о реализации: стейджинг версий и неизменяемое хранилище эмбеддингов RAG

## Фаза

Реализация фундамента для векторного ретрива по проектному предложению
`docs/rag-embeddings-and-retrieval-design.md` (§2, §4). Жизненный цикл записи версии, который раньше был
одной атомарной операцией `appendVersion` (вставка версии + чанков + активация), **расщеплён на три
шага**: стейджинг → сохранение эмбеддингов → активация. Добавлена неизменяемая таблица
`rag_chunk_embeddings` (миграция `0002`); referential-целостность версий и nullable-указатель активной
версии приведены к нужной форме миграцией `0003`. Контракт `RagDocumentStore` и его две реализации
(PostgreSQL и in-memory) остаются drop-in совместимыми.

В рамках задачи **намеренно не реализованы** (явные запреты): реальная генерация эмбеддингов (векторы
приходят на вход), ретрив, HTTP-эндпоинты, HNSW/ANN-индекс, Dialfire, краулер, планировщик, Prisma,
Supabase SDK, внешние API эмбеддингов. Миграция `0001` не переписана; директория `dialfire/` не
тронута. Коммит не выполнялся.

## Правки по итогам приёмочного ревью

1. **FK `rag_document_versions → rag_documents` восстановлен (blocker 1).** Первая версия фазы снимала
   этот FK, чтобы стейджить версию нового ключа до появления строки документа. Это отклонено: версия
   обязана принадлежать существующему документу (никаких orphan-версий). Вместо снятия FK **указатель
   `rag_documents.current_version` сделан nullable** (миграция `0003`), а стейджинг нового ключа теперь
   **сначала создаёт строку `rag_documents` с `current_version = NULL`** (активной версии ещё нет), затем
   стейджит `v1` под неизменным FK. Активация лишь продвигает указатель. Добавлен тест, доказывающий
   невозможность создать orphan-версию.
2. **Идемпотентность `saveChunkEmbeddings` уточнена (blocker 2).** Точный повтор той же неизменяемой
   строки — no-op; повтор с тем же натуральным ключом, но **другим вектором/хешами/метаданными**
   теперь **явно падает** (`RagStorageError`) и не проглатывается `ON CONFLICT DO NOTHING`. Сравнение
   содержимого в PostgreSQL выполняется на стороне БД (одинаковая точность `float4`); `created_at`
   исключён из сравнения как «время записи», а не содержимое. Тесты добавлены в оба стора.
3. **Интеграционные тесты не используют `DATABASE_URL` (blocker 3).** Они по-прежнему запускаются только
   при заданном `RAG_TEST_DATABASE_URL` (`describe.skipIf`); он не задан, поэтому сюита пропускается —
   это заявлено как остающийся verification-блокер. Разрушающие тесты против `DATABASE_URL` не
   выполнялись. Миграции применялись к `DATABASE_URL` только как **аддитивный** DDL (`0003`), без
   потери данных.
4. **Исправлено форматирование `docs/rag-embeddings-and-retrieval-design.md` (blocker 4).** Prettier
   убрал два ведущих пробела в строке 358 (косметика markdown-списка); смысл дизайна не изменён.
   `format:check` теперь зелёный.

## Схема данных (миграции `0002` и `0003`)

Миграции forward-only, поверх `0001` (сама `0001` не изменяется):

### `0002_rag_chunk_embeddings.sql`

1. **`CREATE EXTENSION IF NOT EXISTS vector`** — включение pgvector.
2. **Таблица `rag_chunk_embeddings`** (по эскизу §2): идентичность чанка `(document_key,
document_version, chunk_index)` + идентичность эмбеддинга `(embedding_model,
embedding_model_version, embedding_dim, input_recipe, normalized)` + трассируемость (`input_hash`,
   `chunk_content_hash`, `created_at`) + сам вектор.
   - Столбец `embedding vector` **без фиксации размерности** — принимает векторы разной длины от разных
     моделей; `CHECK (vector_dims(embedding) = embedding_dim)` не даёт строке соврать о размерности.
   - `CHECK (embedding_dim > 0)`.
   - `PRIMARY KEY (document_key, document_version, chunk_index, embedding_model,
embedding_model_version)` — один вектор на (чанк × модель × версия модели); re-embedding
     **добавляет** строки, не переписывает.
   - `FOREIGN KEY (document_key, document_version, chunk_index) REFERENCES rag_chunks (…)` — эмбеддинг
     не может существовать без своего неизменяемого чанка.
   - Триггер `rag_chunk_embeddings_immutable` (`BEFORE UPDATE OR DELETE`) — переиспользует
     `rag_forbid_mutation()` из `0001`.
3. **Индекс `rag_chunk_embeddings_model_idx`** по `(embedding_model, embedding_model_version,
document_key, document_version)` — поддержка проверок покрытия/гейта (не векторный индекс).

**Примечание.** `0002` также снимал FK `rag_document_versions → rag_documents`; это решение отменено
миграцией `0003` (см. ниже) и не отражает финальную схему.

### `0003_restore_document_version_fk.sql`

1. **`ALTER TABLE rag_documents ALTER COLUMN current_version DROP NOT NULL`** — активный указатель может
   быть `NULL`, пока у нового документа есть только застейдженная, ещё не активированная версия. `CHECK
(current_version >= 1)` из `0001` сохраняется для любого не-NULL значения.
2. **`ALTER TABLE rag_document_versions ADD CONSTRAINT rag_document_versions_document_key_fkey FOREIGN
KEY (document_key) REFERENCES rag_documents`** — восстановление FK: версия обязана ссылаться на
   существующий документ (никаких orphan-версий). Тем самым «эмбеддинг → чанк → версия → документ» —
   сплошная цепочка внешних ключей.

**HNSW/ANN-индекс намеренно НЕ создаётся** (§5): базовая линия — точный косинусный ретрив; ANN
добавляется позже только по итогам бенчмарка на реальном корпусе.

## Реализованное поведение

### Трёхфазный жизненный цикл (§4)

- **Фаза A — стейджинг (`stageVersion`).** Для нового ключа сначала создаётся строка `rag_documents`
  с `current_version = NULL` (активной версии ещё нет → документ невидим для ретрива), затем под
  неизменным FK вставляются строки версии `N+1` и её чанков. Указатель `current_version` не двигается.
  Проверяется непрерывность номера и правило «не более одной застейдженной версии на документ».
- **Фаза B — эмбеддинги (`saveChunkEmbeddings`).** Append-only. Точный повтор той же строки — no-op;
  повтор с тем же натуральным ключом `(чанк, модель, версия модели)`, но **другим содержимым** (вектор,
  хеши, `dim`/`recipe`/`normalized`) — **явная ошибка `RagStorageError`**, а не тихий пропуск. В
  PostgreSQL: `ON CONFLICT DO NOTHING`, и при `rowCount = 0` — сравнение содержимого на стороне БД
  (`embedding = $::vector AND …`); в памяти — поэлементное сравнение. `created_at` из сравнения
  исключён. Проверяется `embeddingDim === embedding.length` (зеркало `CHECK`) и существование чанка
  (зеркало FK). Повтор после частичного сбоя безопасно досчитывает только недостающее.
- **Фаза C — активация (`activateVersion`).** Под блокировкой документа: повторная проверка
  непрерывности + **гейт готовности эмбеддингов** (активация запрещена, пока хотя бы один чанк целевой
  версии не имеет эмбеддинга активной модели). При успехе указатель `current_version` продвигается
  (строка `rag_documents` уже существует со стейджинга — активация лишь делает `UPDATE`). Старые
  версии/чанки/эмбеддинги не трогаются.

### Инварианты

- **`isActive` не хранится**, а выводится как `version = current_version`. Второй мутируемый флаг не
  вводится.
- **Атомарность активации**: смена активной версии — один сдвиг указателя в одной транзакции;
  наблюдаемого «полу-активного» состояния нет.
- **Безопасный откат**: если эмбеддинг `N+1` не завершён, активной остаётся `N`; `N+1` лежит
  неактивной и доводится повтором эмбеддинга.
- **Одна застейдженная версия на документ**: пока `N+1` не активирована, создать `N+2` нельзя; повтор
  идёт по той же `N+1`.
- **Совместимость сторов**: обе реализации дают одинаковые исходы и одинаковые ошибки `RagStorageError`
  для одинаковых нарушений; ридеры возвращают замороженные представления с выведенным `isActive`.

## Тесты

- **`tests/unit/rag-in-memory-document-store.test.ts`** — стейджинг без активации; первая версия
  обязана быть 1; несоответствие чанка версии/ключу; правило «одна застейдженная версия»; эмбеддинги
  (несовпадение размерности, неизвестный чанк, **идемпотентный повтор с другим `createdAt`**, **отказ
  при конфликте** — другой вектор / другой `input_hash`, разные версии модели рядом); гейт активации
  (неполное покрытие, чужая модель, незастейдженная версия); успешная активация; повтор, досчитывающий
  недостающий эмбеддинг; неизменяемость входов и вектора.

  после активации `N`; отказ стейджить другой контент поверх незавершённой застейдженной версии;
  неизменность неактивных чанков; версионные chunk-key; трассируемость; детерминизм и неизменяемость

  round-trip вектора через pgvector; отсутствие новой версии при неизменном хеше; активация `N+1` с
  сохранением неактивной `N`; атомарность стейджинга; непрерывность номера; «одна застейдженная версия»;
  гейт готовности; **идемпотентность эмбеддингов (включая другой `createdAt`) и отказ при конфликте
  содержимого**; **запрет orphan-версии (FK)**; `CHECK` размерности; неизменяемость версии и эмбеддинга
  на уровне БД. Запускаются только при заданном `RAG_TEST_DATABASE_URL` (`describe.skipIf`).

## Блокеры

- **Интеграционные тесты PostgreSQL не запускались** (blocker 3) — нет отдельной одноразовой
  `RAG_TEST_DATABASE_URL`, а сюита делает `TRUNCATE`. Запускать её против `DATABASE_URL` нельзя
  (уничтожило бы существующие данные). Поэтому **поведенческая** проверка на живой БД тестов orphan-FK,
  идемпотентности/конфликта эмбеддингов, гейта и неизменяемости **остаётся невыполненной** — это
  заявленный verification-блокер. Косвенно проверено: успешное применение миграций к реальному pgvector;
  read-only-инспекция схемы (FK восстановлен, указатель nullable); те же инварианты покрыты
  in-memory-юнит-тестами. Для полной проверки нужно задать одноразовую `RAG_TEST_DATABASE_URL` и
  выполнить `npm test`.

## Допущения и ограничения объёма

- **Векторы не вычисляются.** `saveChunkEmbeddings` принимает уже готовый вектор и метаданные рецепта;
  реальный инференс E5 (`intfloat/multilingual-e5-large`, dim 1024, префиксы, усечение 512 токенов,
  L2-нормализация) — офлайн-шаг Phase 11, вне этой фазы. В тестах используются короткие фиктивные
  векторы.
- **Интеграционные тесты против живой БД не запускались** — см. «Блокеры». `DATABASE_URL` не
  одноразовая (в ней есть данные), а тесты делают `TRUNCATE`; `RAG_TEST_DATABASE_URL` не задан. Миграции
  `0002`/`0003` применялись к `DATABASE_URL` как **аддитивный** DDL и данные не изменяли.
- **Отказ от застейдженной версии не реализован.** Немутирующий маркер «отклонена/заменена»
  (таблица-спутник по `(document_key, version)`) остаётся открытым вопросом (§4); до его введения
  застейдженная версия либо активируется, либо остаётся как есть (и блокирует новый стейджинг).
- **Смена активной модели в рантайме (fail-closed по §3)** как отдельная операция ретрива не
  реализована — она относится к фазе ретрива; в этой фазе есть строительный блок: гейт покрытия при
  активации.
- **`SIMILARITY_MIN`** остаётся `unset` (§6) — калибруется на размеченном наборе в фазе ретрива.
- TLS/SSL — как в предыдущей фазе, несёт сама строка подключения; секреты не читаются, не логируются, не
  коммитятся.
